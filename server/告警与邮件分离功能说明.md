# 告警与邮件分离功能说明

## 📋 功能概述

本次更新将**告警记录**和**邮件通知**拆分为两个独立的开关，实现更灵活的硬件变更监控配置。

---

## 🎯 核心改进

### 之前的行为（有问题）
- ❌ 告警和邮件绑定在一起
- ❌ 开启告警后**必须**发送邮件
- ❌ 无法只记录告警而不发邮件
- ❌ 要关闭邮件只能同时关闭告警

### 现在的行为（已修复）
- ✅ **告警记录开关**（默认开启）- 控制是否在数据库中记录告警
- ✅ **邮件通知开关**（默认关闭）- 控制是否发送邮件通知
- ✅ 两个开关完全独立，可以自由组合
- ✅ 支持4种工作模式

---

## 🔧 四种工作模式

| 告警记录 | 邮件通知 | 效果说明 | 适用场景 |
|---------|---------|---------|---------|
| ✅ 开启 | ❌ 关闭 | 只记录告警，不发送邮件 | **推荐**：日常监控，需要查看历史记录但不想被邮件打扰 |
| ✅ 开启 | ✅ 开启 | 既记录告警又发送邮件 | 重要设备监控，需要即时通知 |
| ❌ 关闭 | ❌ 关闭 | 完全不监控 | 临时关闭监控或测试环境 |
| ❌ 关闭 | ✅ 开启 | **不可能**（邮件依赖告警） | - |

> ⚠️ **注意**：如果关闭了"告警记录"，即使开启"邮件通知"也不会发送邮件，因为没有告警数据可发送。

## 💡 使用示例

### 场景1：日常监控（推荐）
```
✅ 告警记录：开启
❌ 邮件通知：关闭
✅ CPU、GPU、内存、硬盘：开启
```
**效果**：硬件变更会记录到告警列表，可以随时查看历史，但不会发送邮件打扰。

### 场景2：关键设备监控
```
✅ 告警记录：开启
✅ 邮件通知：开启
✅ 所有硬件类型：开启
```
**效果**：任何硬件变更都会记录并立即发送邮件通知管理员。

### 场景3：临时关闭监控
```
❌ 告警记录：关闭
❌ 邮件通知：关闭
```
**效果**：完全不监控硬件变更，适用于维护期间或测试环境。

### 场景4：仅监控关键硬件
```
✅ 告警记录：开启
❌ 邮件通知：关闭
✅ CPU、GPU：开启
❌ 其他硬件：关闭
```
**效果**：只监控CPU和GPU的变化，其他硬件变化忽略。

## 🔄 数据库变更

### 新增字段

在 `alert_settings` 表中添加了两个新字段：

```sql
ALTER TABLE alert_settings 
ADD COLUMN alert_enabled TINYINT DEFAULT 1 COMMENT '告警开关',
ADD COLUMN email_enabled TINYINT DEFAULT 0 COMMENT '邮件开关';
```

### 自动迁移

- ✅ 首次启动时会自动检测并添加缺失的字段
- ✅ 不会影响现有数据
- ✅ 迁移失败不会中断服务启动

## ⚠️ 注意事项

1. **默认配置**：
   - 告警记录：**开启**（保持向后兼容）
   - 邮件通知：**关闭**（避免意外发送邮件）

2. **恢复默认**：
   - 点击"恢复默认"按钮会将告警设为开启，邮件设为关闭

3. **邮件依赖**：
   - 邮件通知需要先配置邮件服务器（SMTP设置）
   - 即使开启邮件通知，如果邮件配置不正确也不会发送

4. **性能影响**：
   - 关闭告警记录可以减少数据库写入操作
   - 关闭邮件通知可以避免网络请求延迟

## 🆘 常见问题

### Q1: 为什么我开启了邮件通知但没有收到邮件？
**A**: 请检查：
1. 告警记录是否开启（必须先开启）
2. 邮件配置是否正确（SMTP设置、收件人）
3. 是否有硬件变更触发告警
4. 查看服务端日志确认邮件发送状态

### Q2: 我想关闭所有监控，怎么操作？
**A**: 只需关闭"告警记录"开关即可，这样无论硬件如何变化都不会记录和发送邮件。

### Q3: 升级后我的旧配置会丢失吗？
**A**: 不会。升级会自动保留原有配置，新字段使用默认值（告警开启、邮件关闭）。

### Q4: 可以只发送邮件不记录告警吗？
**A**: 不可以。邮件通知依赖于告警记录，没有告警数据就无法发送邮件。这是设计上的逻辑关系。
